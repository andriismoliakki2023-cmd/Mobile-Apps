# :bookmark_tabs: Лабораторна робота №1
## Тема: "Основи розробки інтерактивних мобільних застосунків на Flutter"

### 1. Мета роботи
Опанування базових принципів розробки мобільних застосунків на платформі Flutter, набуття практичних навичок створення інтерактивних UI-компонентів, управління станом застосунку та налаштування середовища розробки.

---

### 2. Завдання до лабораторної роботи

**Мета завдання:** Розробити мобільний застосунок на платформі Flutter, який демонструє принципи реактивного програмування шляхом управління локальним станом та обробки користувацького введення.

**Функціональні вимоги:**
1. **Компонент введення даних:** Реалізація текстового поля (наприклад, `TextField`), яке здійснює захоплення та первинну обробку даних, введених користувачем.
2. **Динамічне оновлення інтерфейсу:** Забезпечення перемальовування графа (дерева) віджетів (Widget Tree) у реальному часі як реакції на зміну стану системи.
3. **Механізм валідації:** Впровадження синтаксичного та логічного контролю вхідного потоку даних перед ініціацією будь-яких операцій зі станом застосунку.

**Критерії приймання (Acceptance Criteria) та бізнес-логіка:**
Додаток повинен реалізовувати механізм лічильника, стан якого змінюється виключно за такими правилами:
- **Сценарій 1 (Математична операція):** При успішному парсингу введеного рядка у цілочисельний формат (Integer), система виконує інкремент поточного значення лічильника на введене число (включаючи від'ємні значення, якщо такі передбачені логікою студента).
- **Сценарій 2 (Термінальна команда):** При введенні точного текстового значення `"Avada Kedavra"` система ініціює примусове обнулення стану лічильника (скидання до `0`).
- **Сценарій 3 (Обробка виключень):** Введення будь-яких інших даних (текст, спецсимволи, дробові числа) класифікується як невалідний стан. Система повинна перехопити цю подію, проігнорувати зміну лічильника та вивести відповідне інформаційне повідомлення для користувача (наприклад, через `SnackBar` або текстовий віджет помилки), зберігаючи стабільність роботи застосунку.

**Технічні та архітектурні обмеження:**
- **Управління станом:** Для збереження та мутації даних лічильника обов'язковим є використання базового підходу з використанням `StatefulWidget` та виклику методу `setState()`.
- **Якість коду:** Вихідний код повинен повністю відповідати правилам статичного аналізатора (Dart Linter). Наявність попереджень (warnings) при компіляції є підставою для зниження оцінки.
- **UI/UX складова:** Інтерфейс має бути інтуїтивно зрозумілим. Вимагається застосування базових принципів композиції віджетів, коректного позиціонування елементів на екрані та забезпечення візуального зворотного зв'язку при помилках валідації.

### 3. Порядок виконання

#### 3.1. Налаштування середовища розробки
1. Встановити Flutter SDK згідно з офіційною інструкцією [Flutter Install](https://flutter.dev/docs/get-started/install).
2. Налаштувати редактор коду (Android Studio / VS Code) згідно з [офіційними рекомендаціями](https://flutter.dev/docs/get-started/editor).
3. Переконатися у працездатності середовища командою:
   ```bash
   flutter doctor
   ```

#### 3.2. Створення базового проєкту
1. Створити новий проєкт:
   ```bash
   flutter create my_project
   ```
2. Перейти до каталогу проєкту:
   ```bash
   cd my_project
   ```
3. Запустити застосунок для перевірки:
   ```bash
   flutter run
   ```

#### 3.3. Налаштування статичного аналізу коду
1. Створити файл `analysis_options.yaml` у корені проєкту.
2. Розмістити в ньому конфігурацію лінтингу згідно з наданим шаблоном (файл доступний у репозиторії).
3. Усі подальші зміни коду мають відповідати правилам аналізатора.

#### 3.4. Реалізація основного функціоналу
1. Модифікувати файл `lib/main.dart` або створити додаткові файли для реалізації логіки.
2. Реалізувати Stateful-віджет для керування станом лічильника та полем введення.
3. Додати логіку валідації введених даних згідно з завданням.
4. Забезпечити динамічне оновлення інтерфейсу при зміні стану.

**Додаткові вимоги:**
- Використовувати [Dart Linter](https://dart.dev/tools/dartfmt) для форматування коду.
- Оптимізувати структуру проєкту, видаливши непотрібні папки платформ (залишити лише `android/` та `ios/`).

#### 3.5. Автоматизація перевірки коду
1. Створити директорію `.github/workflows/` у корені проєкту.
2. Додати файл `validation.yaml` з наданою конфігурацією CI/CD.
3. Налаштувати автоматичну перевірку коду при створенні Pull Request.
